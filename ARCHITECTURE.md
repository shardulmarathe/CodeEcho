# Architecture

How CodeEcho is put together: the two product modes, the scoring pipeline, the
RAG layer that grounds it, and the cost guards that keep a free-tier stack from
producing a bill.

## What the product does

You answer real software-engineering interview questions **out loud**. CodeEcho
transcribes you and scores two independent axes:

- **Reasoning / content**. STAR (behavioral) and technical rubrics, scored
  per-dimension 1–5 with rationale, evidence, and a concrete suggestion. Grounded
  by a retrieval corpus so the feedback is specific rather than generic.
- **Delivery**, filler words, words per minute, pauses, and idea transitions.
  These are objective and measurable, which is what anchors the credibility of
  the more subjective content score.

Two modes:

| Mode | Route | What it is |
|---|---|---|
| **Mock Interview** | `/interview` | A guided multi-question session with dynamic LLM follow-ups. Scores stay hidden until one combined report at the end. |
| **Practice** | `/practice` | A single question → score → retry loop, with results shown immediately. |

Questions are either generated by the app or brought by the user, paste your
own and the model classifies its type, track and bucket.

## Stack

- **Frontend**. Next.js 16 + React + Tailwind, with a bespoke dark/sketch design
  system rather than a component library. Deployed to Vercel.
- **Backend**. FastAPI (Python 3.10+), containerized via `backend/Dockerfile`,
  deployed to Render as a Docker web service. **Single-process, single-worker on
  purpose**, several caches are in-memory and correctness depends on it.
- **Data**. Supabase: Postgres, Storage (private audio bucket behind signed
  URLs), and pgvector for retrieval. Storage and database only; no application
  code runs there.
- **LLM**. Gemini, through whichever of three providers is auto-detected from
  the key shape in `services/llm_client.py`: the Stanford `api.llm.stanford.edu`
  proxy (Gemini REST format, `sk-` key, the default), the Stanford UIT gateway
  (OpenAI-compatible), or Google direct (`AIza` key).
- **Speech-to-text**. Azure OpenAI Whisper, preferred for its native word-level
  timestamps. Falls back to mock data when no key is present, so the app runs
  offline.
- **Auth**. Clerk, with the backend verifying session JWTs via JWKS/RS256.
  Guest mode with claim-on-signup.
- **Audio**. FFmpeg, for filler-clip generation.

## How a practice attempt flows

1. Pick a type (behavioral / technical / bring-your-own) and seniority; a
   `Question` is generated or the pasted one is classified.
2. Record in-browser. Recording auto-stops at **90 seconds**.
3. `POST /attempts` → upload audio → an SSE stream carrying Whisper
   transcription, then filler/pause/pace metrics, then idea-transition tagging.
4. `POST /attempts/{id}/score` returns a retrieval-grounded scorecard.
5. The UI shows delivery first, then the content dimensions, with a retry loop
   offering progressive hints and an on-demand model answer.

## Mock-interview orchestration

A session is an **immutable plan** of main-question specs plus an **append-only
turns log**. Every cursor, current turn, follow-ups asked, is *derived* from
that log rather than stored as a mutable counter, which is what makes `/advance`
idempotent.

The plan varies by mode: behavioral spreads about three mains across the three
buckets; technical coding runs three problems escalating easy → medium → hard;
system-design and project modes use a single main with heavy follow-ups. The caps
live in `interview.py`.

Every turn, main or follow-up, is an ordinary attempt, reusing the whole
record → transcribe → metrics pipeline unchanged. Follow-ups are decided by the
model (`generate_followup` returns a `Question` or `None` to move on) and inherit
the parent's track, bucket, competency and seniority so scoring needs no special
case. On any failure it degrades to `None`, so a follow-up can never block the
session.

Scores stay hidden until the final report, which leads with a single generalized
rubric covering the whole interview, one `score_interview` call producing
dimensions, a verdict, strengths, improvements and follow-up handling. Per-turn
scorecards are fetched on demand from each turn's `attempt_id`.

## Latency

LLM round-trips were the dominant cost, addressed three ways:

- **`thinkingBudget:0`** on generation, classification and follow-up calls, which
  takes them from roughly 5s to 1s. Scoring keeps a real budget, it is
  output-bound, and runs turns concurrently through a `ThreadPoolExecutor`.
- **Main-question prefetch.** Main questions are fixed by the plan and therefore
  answer-independent, so the next one is generated in a FastAPI `BackgroundTask`
  during the candidate's answer window and stored on the session. This is only
  safe because the backend is single-worker.
- **Parallel `/advance`.** The frontend hands back the attempt id early and runs
  `/advance` concurrently with transcription, passing the browser's live
  transcript; `/advance` accepts it as an override for the follow-up decision and
  falls back to the sequential path when absent. Main → main transitions become
  near-instant, and main → follow-up drops from `transcription + LLM` to roughly
  `max(transcription, LLM)`.

## Retrieval

Retrieval grounds the **scorer**, not answer generation.

1. **Embed**, local `fastembed BAAI/bge-base-en-v1.5` (768-dim, offline) by
   default, or Google `text-embedding-004` when an embedding key is set. Note the
   Stanford gateway offers no embedding model.
2. **Hybrid retrieve**, dense pgvector (HNSW) plus Postgres full-text, fused
   with Reciprocal Rank Fusion in SQL, under a strict bucket filter. Degrades to
   dense-only, then to a local JSON index.
3. **Rerank**, a local cross-encoder reorders a pool of 20 down to the top 4.
   Any failure falls back to input order.
4. The top-k is injected into the scoring prompt and the model answer.

The corpus is roughly 1,865 chunks across coding, system design, project,
learning, experience and introspection. Ingest PDFs from
`backend/data/kb_sources/<bucket>/` with `python -m scripts.ingest_kb`.

The reranker (~200MB of ONNX) is **disabled on Render**, where the 512MB free
tier OOMs during scoring; `RENDER=true` skips its warm-up. Hybrid retrieval still
runs without it.

## Cost and safety guards

**Never producing a surprise bill is a hard requirement**, not a preference.
Abusive or excessive traffic must be rejected, never billed.

- A global **$3/day** estimated-spend cap, plus per-user ($0.50) and
  per-guest-IP ($0.15) caps in `budget.py`, durable in Supabase
  `api_usage_daily`.
- Per-IP rate limits, a 90-second answer cap, and a 25MB upload cap. Abuse
  returns 402 or 429 rather than spending.

Security properties worth not regressing:

- The API key travels in a header, never in a URL.
- Media routes are guarded against path traversal.
- Debug routes are **off by default**, they are unauthenticated and would let
  anyone spend the LLM budget. Enable only locally.
- Client errors are generic.
- Prompt-injection guard in the scoring and follow-up prompts: the transcript and
  scratchpad are treated strictly as data, never as instructions.

## Deployment

The backend cannot go to Vercel or Supabase, it needs a long-lived process for
its in-memory session cache. Render's free tier suits it: 750 instance-hours a
month, no card required, and it **suspends rather than bills** when exhausted,
which is what makes the no-surprise-bill guarantee hold. It sleeps after 15
minutes idle, so expect roughly a one-minute cold start.

Google Cloud Run was rejected for the backend because it requires a billing
account and its budgets are alerts rather than hard stops.

`render.yaml` is the deployment blueprint. Every secret is marked `sync: false`
so no value is ever committed; set them in the Render dashboard. `supabase/`
holds the schema and row-level-security policies, applied manually.
